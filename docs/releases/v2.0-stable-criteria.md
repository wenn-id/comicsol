# Comic Sol v2.0.0 Stable Release Criteria

Status: **authoritative release gate**

Applies to: the first stable `v2.0.0` tag and every release candidate that claims v2.0 readiness.

This document is the single checklist for answering **“is Comic Sol v2.0 ready?”**. A checked item requires current, reproducible evidence from the exact release candidate commit. Passing unit tests alone is not sufficient. Items that depend on work tracked by a P0/P1 issue remain unchecked until that issue is implemented and verified.

## Release decision

A stable tag may be cut only when all of the following are true:

- [ ] Every mandatory criterion in this document has current evidence.
- [ ] The release qualification workflow is green for the exact candidate commit.
- [ ] No open P0 or P1 issue remains, unless the issue is explicitly reclassified and the release decision records the rationale.
- [ ] No unresolved release-blocking review thread, security alert, or known data-loss/install blocker remains.
- [ ] A maintainer records the candidate commit, test/workflow URLs, artifact checksums, and the final decision in the release notes.

A release candidate can be published only after the exact candidate SHA passes the full platform tests (including `pip-audit`), release-blocking quality, CodeQL, and benchmark gates. The production orchestration starts only from a `push` of a canonical `v*` signed annotated tag whose package version matches exactly. Preparation captures the immutable annotated tag-object SHA and peeled candidate commit, fetches protected `main` freshly, and requires the candidate to be an ancestor of that fetched `main`; the triggering ref/SHA, checkout, package, tag object, and peeled commit must agree. Every GitHub Release must retain the exact `tag_name`; because GitHub may report `target_commitish: main` when that tag already exists, raw `target_commitish` is non-authoritative and the Release target is resolved instead from the captured direct annotated tag-object SHA and peeled candidate commit in remote refs. The published candidate remains an immutable GitHub prerelease; after qualification and protected approval, production status is represented by the protected deployment, attested evidence, and an allowed title/release-notes marker rather than by changing GitHub's locked prerelease field.

The gates are intentionally strict and blocking for pull requests, `main`, and exact release candidates. Ruff lint and Ruff formatting must pass with only the documented repository-bootstrap import exception; mypy covers the trust boundary plus incremental CLI, MCP, lifecycle orchestration, and release scopes. Coverage measures application source separately from tests and fails below 82% line coverage or 72% branch coverage. Repository administrators must require the stable `Quality gates` status on `main` branch protection so those floors and checks cannot be bypassed during merge. Repository administrators must also enable [GitHub immutable releases](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/immutable-releases), configure active tag rulesets whose GitHub-compatible matching conditions cover `refs/tags/v*` and collectively restrict tag creation, updates, and deletions and enable `required_signatures`, and configure the `release-production` Environment with required reviewers and prevention of self-review before creating the next candidate. The resulting effective policy restricts tag creation, updates, and deletions. For this personal repository, the only trusted release-creation bypass is repository admin: `actor_type: RepositoryRole`, `actor_id: 5`, `bypass_mode: always`. Write or maintain roles, teams, integrations, pull-request-only mode, malformed actors, and unsupported or malformed ref patterns are rejected fail-closed. Every matching ruleset containing `creation` must contain exactly that approved actor. Trusted tag signers still require explicit maintainer review. The workflow does not weaken these requirements or configure repository settings. If the effective tag rulesets or approved authority are absent, preparation fails before builds; if publication does not return `immutable: true`, publication fails closed and deletes only the newly created, run-owned mutable candidate best-effort. Promotion accepts only an immutable release.

## Release orchestration states

The one release orchestration run owns the state transition; passing checks from another run or SHA never count.

1. **Candidate prepared:** a `push.tags: v*` run requires a signed annotated tag and captures its direct tag-object SHA separately from its peeled candidate commit. It proves that `github.ref` is the exact tag ref; the triggering SHA, local tag, and checkout identify that candidate; the package version and release notes match; and the GitHub tag API reports the captured object signature as verified. It fetches `origin/main` freshly and requires the candidate to be an ancestor of the captured protected-main SHA. The workflow also fails closed unless the active tag rulesets matching the exact ref collectively restrict creation, updates, and deletions and enable `required_signatures`; exclusions win, `*` never crosses `/`, `**` may, and unsupported patterns are rejected. Every effective bypass actor must be exactly repository admin (`RepositoryRole`, actor ID `5`, mode `always`), and every matching ruleset containing `creation` must contain exactly that actor. The canonical matching ruleset IDs and approved authority are captured for downstream evidence. Same-tag runs are serialized and no release exists yet.
2. **Candidate gated and built:** full tests including `pip-audit`, strict Ruff/format/mypy/coverage quality, CodeQL, and benchmark pass for that SHA. A sanitized `visual-evidence/manifest.json` is published after the candidate on the separate immutable commit named by the protected `V2_2_LIVE_VISUAL_EVIDENCE_SHA` repository variable, and must independently match `V2_2_REVIEWER_ATTESTATION_SHA256`; the validator requires the exact candidate SHA/version, reviewer approval, complete score and material-change coverage, and all visual thresholds before it creates the deterministic public archive and summaries. Native, source, container, and visual evidence jobs consume the same candidate SHA and upload their only outputs as Actions artifacts.
3. **Candidate published:** at every mutation boundary the workflow reads both remote refs and requires the direct ref to equal the captured annotated tag-object SHA and the peeled ref to equal the captured candidate commit; deletion, a lightweight tag, a moved tag, and replacement with a different tag object are all fatal even when the peeled commit is unchanged. It creates a private draft candidate through the Releases API while retaining its returned ID and a current-run ownership marker for cleanup, validates both the creation response and a fresh draft read so `tag_name` equals the captured tag and freshly resolved remote refs retain the captured direct annotated tag-object SHA and peeled candidate commit. Raw `target_commitish` is not target evidence for this existing-tag flow. It uploads every asset once without `--clobber`, and downloads and verifies the complete byte set while it is still a draft. It repeats the tag-object/commit check immediately before publication, publishes the draft as a public prerelease, revalidates the exact Release `tag_name` plus its target resolved through the direct tag-object SHA and peeled candidate commit, requires `immutable: true`, and repeats the exact remote identity check once more. GitHub then locks the release assets and associated tag; a mutable publication is deleted best-effort only when its ownership marker matches this run. `SHA256SUMS`, its Sigstore bundle, payload provenance attestations, `candidate-identity.json`, its digest, and its separate build-provenance attestation bind the tag-object SHA, candidate commit, protected-main SHA, canonical matching ruleset IDs, approved repository-admin bypass authority, run, immutable Release target, and bytes. Any retry that changes published bytes requires a fresh version and tag.
4. **Qualification:** the reusable qualification workflow downloads the public candidate assets, verifies `candidate-identity.json` provenance under the exact release workflow/tag/commit before trusting its policy fields, repeats protected-main ancestry and exact direct/peeled remote tag identity checks, requires fresh Release and remote-ref reads in both the identity and aggregate jobs to prove the exact `tag_name`, captured direct tag-object SHA, and peeled candidate commit and requires `draft=false`, `prerelease=true`, and `immutable=true`, strictly verifies the signed manifest and tag/SHA/workflow-bound provenance, checks the published native/source/container bytes, verifies all three live visual payload attestations and digests, and independently requires the visual summary to remain candidate-bound and `PROMOTION APPROVED` before it emits a fail-closed aggregate decision plus its SHA-256. The aggregate job repeats the immutable-state read before it can emit `RELEASE READY` and refuses to proceed unless the identity job succeeded. Manual `workflow_dispatch` remains a qualification recovery path but requires the tag, exact candidate SHA, captured tag-object SHA, protected-main SHA, canonical matching ruleset IDs, and approved bypass identity; all must equal the immutable `candidate-identity.json`. Production orchestration itself has no manual trigger.
5. **Awaiting approval:** a successful candidate waits at the named `release-production` GitHub Environment. Repository administrators must configure required reviewers and prevent self-review where available; YAML can name but cannot protect an Environment. The promotion job also queries the Environment protection rules and fails closed unless both controls are present. Until that repository setting exists, the approval control is not operationally complete and no production release can be promoted.
6. **Promotion:** after approval, the final job downloads the candidate again, compares every byte to the candidate identity and signed manifest, binds the downloaded benchmark, live visual, and qualification JSON files to their current-run output hashes, and records the exact current-run Actions artifact and deployment identities. On a retry, it deterministically chooses the newest deployment status linked to the run and records `github.run_attempt`. It writes `release-evidence.{json,md,sha256}`, preserves them as a run-attempt-specific Actions artifact, and attests their checksums under the release workflow's OIDC identity. It then verifies the evidence checksums, re-reads the immutable prerelease and freshly validates its exact `tag_name`, direct tag-object SHA, and peeled candidate commit at the initial promotion check, final preflight, and immediate mutation boundary. The protected deployment and attested evidence are the production promotion decision; the final allowed Release mutation changes only the title and release notes to record that decision and link the evidence. It never changes the locked prerelease field and never rebuilds, replaces, deletes, or re-signs payloads. Configured eligible reviewers are recorded separately from the nullable actual approver; no eligible reviewer, `github.actor`, or trigger actor is claimed to be the actual approver.
7. **Failure / blocked:** a pre-draft failure creates no release. A normal failed draft is deleted best-effort without deleting the tag; creation captures the API response ID directly, and response-loss cleanup may resolve an exact same-tag fallback only when its embedded run/attempt ownership marker matches the current serialized run. A publication that is not immutable is deleted best-effort under that same ownership check and cannot qualify or promote. If cancellation leaves a private draft behind, an administrator must verify that it was never public, delete only that draft, and rerun the unchanged tag. A partial candidate, missing or unapproved live visual evidence, missing summary, failed/exception qualification, identity mismatch, or denied approval remains blocked and cannot promote. If promotion is interrupted after evidence artifact upload but before the final PATCH, the immutable public release remains a prerelease candidate; a new approved attempt selects its newest run-linked deployment and emits a separately named run-attempt evidence artifact and attestation. Never move or reuse the tag and never replace payloads.
8. **Withdrawal / yank:** edit the immutable release title and notes to say withdrawn, or remove its public release entry while retaining the tag, run evidence, reason, and incident link. The locked assets and prerelease state are never rewritten. This workflow does not publish PyPI or registry payloads, so it must not claim to yank those systems. The step-by-step procedure is the [`rollback-runbook.md`](rollback-runbook.md) withdrawal section.
9. **Rollback:** edit the release title/notes to say rolled back, mark the production deployment blocked/inactive as repository policy permits, and direct users to the last qualified version. Do not rebuild the old tag, replace assets, or claim that the immutable prerelease field was changed. Link the rollback action and deployment audit from the evidence/incident record. The step-by-step procedure is the [`rollback-runbook.md`](rollback-runbook.md) rollback section.

### Disposable-candidate drill

The deterministic contract drill is exercised by `tests.test_release_qualification.ReleaseOrchestrationContractTests`: it builds canonical evidence for a disposable candidate, rejects a failed qualification and a benchmark regression, verifies that the trigger actor is not represented as the approver, and checks the no-clobber/no-rebuild workflow contracts. Before enabling stable production promotion, maintainers must also run a fresh disposable tag through GitHub, deliberately block one qualification, withdraw that candidate, then run a fresh tag through `release-production`; link both runs and deployment-review records in the release issue. A local test cannot substitute for that live Environment drill.

## 1. Supported clean-install targets

Each target must be qualified from the intended release artifact, not only from a source checkout:

- [ ] Linux x86_64 native bundle and installer.
- [ ] macOS arm64 native bundle and installer.
- [ ] Windows x86_64 native bundle and PowerShell installer.
- [ ] WSL2 using the Linux instructions and Linux artifact; native Windows PowerShell qualification is separate.
- [ ] Each target reports `comic-sol --version` and `comic-sol doctor` successfully after installation.
- [ ] Each target runs a minimal local fixture lifecycle without a live image provider.
- [ ] Each target verifies uninstall and confirms that user projects and separately managed client configuration survive.
- [ ] Platform-specific exceptions are recorded in the qualification summary; skipped work is not treated as passed.

The supported platform contract separates two channels. Native archives are Linux x86_64,
macOS arm64, and Windows x86_64. WSL2 uses the Linux x86_64 archive; it has no separate
native archive. Source installation supports Linux, macOS, Windows, and WSL2 on Python 3.11+.
Intel macOS is source-install-only; it has no native archive. Native bundles must not require
a system Python.

## 2. Required CLI and project lifecycle

The following commands must be exercised on a clean project and on a representative existing project where applicable:

- [ ] `doctor` reports runtime, version, bundled templates/fonts/references, writable locations, and MCP/configuration capability status with actionable failures.
- [ ] `init` creates a valid editable project with the expected manifest and initial state.
- [ ] `status` reports the project state without fabricating completed work.
- [ ] `validate` accepts valid projects and rejects malformed or unsupported state non-destructively.
- [ ] `resume` produces a deterministic resume plan and reruns only stale work plus dependents.
- [ ] `finalize` publishes terminal artifacts only after required QA and validation gates pass.
- [ ] `setup` and `repair` preserve existing configuration on success and roll back safely on failure.
- [ ] `uninstall` removes only product-owned runtime files, is safe to repeat, and preserves user projects.
- [ ] The MCP lifecycle exposes the same safety and state semantics as the CLI where the operation is shared.
- [ ] Human output remains readable and machine-readable output preserves the documented `ok`, `command`, `data`, and `error` envelope.

## 3. Interrupted generation and resume

- [ ] An interruption after one or more accepted panels preserves those accepted artifacts byte-for-byte.
- [ ] Incomplete, failed, missing, or stale artifacts are identified as actionable resume work rather than treated as accepted output.
- [ ] Resume after QA failure, missing artifact, selective repair, and process termination is covered.
- [ ] Remaining stages continue from the earliest invalid stage and do not regenerate valid accepted work.
- [ ] Running resume repeatedly is safe and idempotent.
- [ ] Manifest state, event log, provenance, attempts, and cache evidence remain internally consistent.
- [ ] No stage advances to completed without its required artifact and validation evidence.

## 4. Project-data preservation and lifecycle safety

- [ ] Upgrade over an existing installation preserves user projects and unrelated files.
- [ ] An injected upgrade failure restores the previous usable runtime or leaves an explicit recoverable state.
- [ ] Normal, repeated, and post-reinstall uninstall operations are safe.
- [ ] Sentinel files outside product-owned paths survive install, upgrade, rollback, repair, and uninstall.
- [ ] Client configuration is preserved or transactionally restored when a mutation fails.
- [ ] Migration failures preserve the original project and identify the required recovery action.
- [ ] Project schema compatibility is documented, unsupported versions fail clearly, and compatible legacy fixtures are tested.

## 5. Release artifacts, integrity, and provenance

For the exact candidate version and commit:

- [ ] Linux x86_64, macOS arm64, and Windows x86_64 native archives are built on their corresponding native runners.
- [ ] Source wheel and sdist are built and validated.
- [ ] Installers, archives, and package artifacts are included only when their validation succeeds.
- [ ] The sanitized live visual archive and JSON/Markdown summaries are validated against the exact candidate and independently configured reviewer-attestation digest, published as attested payloads, and report `PROMOTION APPROVED`.
- [ ] `SHA256SUMS` covers every published payload and is independently verified before publication. Candidate identity, its digest, the signed-manifest bundle, and later promotion evidence are supporting evidence outside that payload manifest so their own checksums do not create cycles.
- [ ] Each native bundle contains deterministic metadata and a valid CycloneDX SBOM describing that bundle.
- [ ] Build provenance attestations cover every payload named by the signed manifest, including native archives, source packages, installers, metadata, SBOMs, and the exported container tar.
- [ ] Every dependency lock is generated from a canonical input file with a reproducible regeneration command, and lock changes are regenerated on Linux, macOS, and Windows and reviewed as per-platform diffs (`requirements/README.md`).
- [ ] Package version, signed annotated release tag, immutable tag-object SHA, candidate commit, protected-main ancestry, release notes, GitHub Release target, and artifact names agree exactly.
- [ ] Documentation includes supported platforms, installation, upgrade, rollback, uninstall, checksum verification, pre-execution installer verification, and known limitations.
- [ ] Signing/notarization status is stated accurately; unsigned artifacts are never described as signed.
- [ ] A clean installation and minimal lifecycle are run against the assembled release artifact.

The release workflow in `.github/workflows/release.yml` is the implementation of the artifact gate. It must check this document before preparing a release and must build all downstream jobs from the exact prepared commit. The complete release subject set and trust chain — including the OCI distribution decision — is defined in [`release-trust-chain.md`](release-trust-chain.md), and the operational rollback/yank procedures that preserve immutable evidence are in [`rollback-runbook.md`](rollback-runbook.md).

## 6. Quality, security, and issue policy

- [ ] Full unit/integration tests, platform matrix, package build, doctor, and repository quality gates pass on the exact candidate commit.
- [ ] Golden pipeline, interrupted-resume, failure-injection, clean-install, and installer lifecycle suites are present and green when their corresponding P0 criteria are enabled.
- [ ] Required security checks, dependency checks, CodeQL, and release validation are green.
- [ ] No open P0/P1 issue remains at the release decision point. Current v2.0 stability P0 roadmap issues are tracked as #108–#117; each must be closed or explicitly reclassified before a stable tag.
- [ ] No known security, data-loss, archive-integrity, path-containment, rollback, or uninstall blocker remains.
- [ ] The release notes link the qualification evidence and identify any non-blocking limitations.

## Evidence record contract

Promotion writes `release-evidence.json`, `release-evidence.md`, and `release-evidence.sha256` without modifying the immutable candidate bytes, tag, or prerelease state. It stores all three in a run-attempt-specific Actions artifact and attests the JSON and Markdown digests from the checksum file under the release workflow identity. This independent anchor remains verifiable even though immutable publication prevents adding evidence assets later; the final Release PATCH changes only title and notes to link the production decision. The machine-readable record links:

- candidate tag, signed annotated tag-object SHA, exact candidate commit, captured protected-main SHA, canonical matching tag-ruleset IDs, exact approved repository-admin bypass identity, immutable Release target/state, orchestration run ID/URL, candidate release, and the current run's available Actions artifact IDs, names, service digests, API URLs, and archive URLs;
- full tests/`pip-audit`, release-blocking quality, CodeQL, the benchmark decision plus the verified `summary-delta.json` SHA-256, and the candidate-bound live visual decision, summary digest, reviewer-attestation digest, Actions artifact, and three attested release payloads;
- the signed checksum manifest and digest, every payload checksum, SBOM URL, and repository attestation location;
- per-platform and aggregate qualification summaries plus the verified `release-summary.json` SHA-256;
- the exact `release-production` deployment ID, candidate SHA, Environment, API URL, and Actions-run HTML audit URL;
- configured required-reviewer identities separately from the actual reviewer. An eligible reviewer is not proof that person approved. The actual reviewer remains `null` when the API cannot safely expose it, and neither `github.actor` nor the trigger actor is substituted.

The versioned release notes or incident record should link this evidence and record open issue disposition and known limitations. A compact human checklist is:

```text
Candidate tag/commit:
Orchestration workflow/run:
Signed manifest/checksum digest:
SBOM/provenance/attestations:
Benchmark artifact/decision:
Live visual artifact/decision/reviewer attestation:
Qualification artifact/decision:
Protected Environment deployment audit:
Open P0/P1 issues:
Known non-blocking limitations:
Decision: PROMOTED / BLOCKED / WITHDRAWN / ROLLED BACK
```
